Engineering approach

Correctness first. Performance claims second.

The repository should make it possible to understand what was implemented, how it was checked, and exactly what a measurement does—and does not—show.

01

Reference path

Start with a readable implementation that defines shapes, semantics, dtypes, and expected outputs.

02

Correctness suite

Test edge cases, numerical tolerances, cancellation behavior, cache ownership, and deterministic cleanup.

03

Named conditions

Record hardware, software versions, shapes, warm-up, sample method, and the exact comparison baseline.

04

Published limits

Keep unsupported features and slower results visible instead of turning a local measurement into a general claim.
